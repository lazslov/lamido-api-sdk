## 2. Invoice webhooks — a consumer surface the SDK does not cover `[SDK]`

The phase-4 plan said invoice-service "never calls you". That is no longer true: since the
service's `8eec4e8`, it emits `invoice.created`, `invoice.failed` and `invoice.canceled`
([invoice-service/webhooks.md](../../../knowledge-base/invoice-service/webhooks.md)). The
signing scheme equals payment's: `{timestamp}.{raw body}`, HMAC-SHA-256, `X-Signature`,
`X-Signature-Timestamp`, dedupe on `X-Event-Id`. The KB now also publishes the estate-wide
receiver contract (WH-27, six items) in every emitting folder.

The SDK ships webhook verification for payment and for content revalidation, and nothing
for invoice. A consumer that receives invoice events today writes their own verifier.

**Tasks:**

- [ ] Add `verifyInvoiceWebhook` and `parseInvoiceWebhookEvent` to `@lazslov/invoice`,
      mirroring payment's shape. Pin fixtures the same way (generated with `node:crypto`,
      non-ASCII case included).
      → verify: fixture suite passes on Node 20.19, 22, and the stripped edge environment.
- [ ] Add an `@lazslov/invoice/next` route handler that encodes the WH-27 receiver
      contract: verify before parse, dedupe on `X-Event-Id` (not `X-Delivery-Id`), answer
      `2xx` for an unrecognised `event_type`, `500` without `markProcessed` when `onEvent`
      throws. Reuse payment's handler pattern.
      → verify: the phase-6 handler criteria, re-run for invoice.
- [ ] Correct the stale claim in [plans/README.md](README.md) ("invoice has no webhook")
      and the phase-6 dependency note.
      → verify: the sentence cites the KB's current text.
- [ ] Note in the docs: the invoice retry ladder runs on a twice-daily cron, so the
      published intervals are floors. A receiver must keep a reconciliation poll —

**Open question for this task:** the 30-day `pdf_url` inside webhook bodies is under

## 5. New services in the knowledge base — candidate packages `[decision]`

The KB now documents four consumer-facing services the SDK does not cover. Each folder is
complete (openapi.yaml, conventions, consumer tiers, webhooks). None of them names an SDK
row yet. A new package follows the phase 3–5 pattern: pin the contract, ship only the
consumer tiers, encode the conventions, verify webhooks, extend the live suite,
`packageDirs`, and the examples import.

| Candidate | Consumer tiers in the KB | Fit for this SDK's audience | Caution |
|---|---|---|---|
| `@lazslov/auth` | `public-api` (browser sign-in), `client-api` (backend authorize, entitlements), webhooks | High — every client site signs people in | Service is at phase 7 of 8; the contract can still move |
| `@lazslov/webshop` | `storefront-api`, public tier, webhooks in both directions | High — commerce sites are the audience | Phase 7 "in flight"; the folder itself lists recent reversals |
| `@lazslov/booking` | `public-api` (`bpk_`, browser-safe), `tenant-api`, webhooks | Medium — sites that book appointments | The service sends nothing; a consumer without a backend gets no notifications. The SDK must not hide that boundary |
| `@lazslov/email` | `tenant-api` (template-only send), webhooks | Low — backend-to-backend, not a client-site concern | Likely out of scope for a consumer SDK; decide, and record the reason |

**Decisions the maintainer owns before any of these become a phase:**

1. Which packages to build, and in what order. A consuming project should pull, as with
   invoice and payment ("follow once a project needs them").
2. Whether to wait for each service to reach phase 8 before pinning its contract. The
   drift protocol handles movement, but a phase-7 service moves often.
3. Whether `@lazslov/email` belongs in a consumer SDK at all.

**Tasks once decided (per package):**

- [ ] Write a `phase-9-<service>.md` plan with exit criteria, in the style of phases 3–5.
- [ ] Add the folder to `contracts/CONTRACTS.json`, `packageDirs`, and the tarball rules —
      the telemetry lesson: a gate driven by a hand-written list will disagree with the
      publisher.
      → verify: `pnpm verify` inspects the new package everywhere the other five are inspected.
