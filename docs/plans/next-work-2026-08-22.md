## 5. New services in the knowledge base — candidate packages `[decision]`

The KB now documents four consumer-facing services the SDK does not cover. Each folder is
complete (openapi.yaml, conventions, consumer tiers, webhooks). None of them names an SDK
row yet. A new package follows the phase 3–5 pattern: pin the contract, ship only the
consumer tiers, encode the conventions, verify webhooks, extend the live suite,
`packageDirs`, and the examples import.

| Candidate | Consumer tiers in the KB | Fit for this SDK's audience | Caution |
|---|---|---|---|
| `@lazslov/auth` | `public-api` (browser sign-in), `client-api` (backend authorize, entitlements), webhooks | High — every client site signs people in | Service is at phase 7 of 8; the contract can still move |
| `@lazslov/webshop` | `storefront-api`, public tier, webhooks in both directions | High — commerce sites are the audience | Phase 7 "in flight"; the folder itself lists recent reversals |
| `@lazslov/booking` | `public-api` (`bpk_`, browser-safe), `tenant-api`, webhooks | Medium — sites that book appointments | The service sends nothing; a consumer without a backend gets no notifications. The SDK must not hide that boundary |
| `@lazslov/email` | `tenant-api` (template-only send), webhooks | Low — backend-to-backend, not a client-site concern | Likely out of scope for a consumer SDK; decide, and record the reason |

**Decisions taken on 2026-09-04** (the maintainer asked for every service to have an SDK):

1. All four, in one phase — `@lazslov/auth`, `@lazslov/booking`, `@lazslov/email`,
   `@lazslov/webshop`. The goal is that a project needing any Lamido service finds a package.
2. Pin now. Every one of the four is at phase 7; the drift protocol reports movement, and a
   package that waits for phase 8 is a package nobody can integrate against meanwhile.
3. `@lazslov/email` ships. Any backend that sends transactional mail is a consumer of the
   tenant tier, and that is the only tier the package exposes.

## 5b. What phase 9 found in the knowledge base `[cross-repo]`

Each is recorded in §7 of the owning package's plan and none is fixed here. **All are filed** —
[knowledge-base#415](https://github.com/lazslov/knowledge-base/pull/415) adds them to that
repository's `docs/backlog.md` as **T-19…T-24**, mirrored to its Asana project. The boxes below
track them from this side; the entries there carry the exit criteria.

**booking-service — two defects the SDK works around, visibly:**

- [ ] Three `operationId`s are declared twice. `openapi.yaml` shares one operation object between a
      path's `get` and its `post` through a YAML anchor, so `cronDrainJobs`, `cronSyncCalendars` and
      `cronMaintenance` each resolve twice and the document is invalid. Give the aliased `post` its
      own id. → the SDK's workaround is `scripts/lib/dedupe-operations.ts`.
- [ ] `example: bsk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx` is credential-shaped, and reached a published
      `.d.ts`. Write it as `bsk_YOUR_SECRET_KEY`. → worked around by `redactExampleCredentials`.
- [ ] `examples.http` §2.59 sends `{ "reason": … }` to `POST /v1/webhook-endpoints/{id}/disable`,
      which reads no body — `disabled_reason` is a fixed string. The example implies a
      caller-supplied reason that does not exist.
- [ ] The published `openapi.yaml` says `409` where conventions.md says `422` for `hold_expired` and
      `already_confirmed`. The folder already records the spec as wrong; the SDK follows the Markdown.

**auth-service:**

- [ ] conventions.md §8 says `Idempotency-Key` is honoured on `POST /v1/admin/keys` **only**, while
      the contract declares the idempotency conflict codes on thirteen operations — five of them
      client-tier. §8 reads like surviving phase-1 scope.
- [ ] `examples.http:141` still says the customer poll omits `poll_interval_ms` on approval;
      `public-api.md` §3 and `examples.http:199` both say T-53 fixed that on 2026-08-27.
- [ ] `webhooks.md` §8 names `GET /v1/entitlements`, which does not exist. The three routes are
      `/v1/subscriptions`, `/v1/plans` and `/v1/features`.

**webshop-service:**

- [ ] `openapi.yaml` is behind its own folder on the cart line: the Markdown records `name` →
      `variant_name` and the three added `product_*` members, and the contract does not.
- [ ] `billing_address` loses its `null` in the contract — an `allOf` artefact collapses
      `(Address | null) & Address` to non-null, erasing the documented "same as shipping" state.

**Estate-wide, and the one worth a decision:**

- [ ] **The webhook envelope is described as identical across services and is not.** auth, booking,
      payment and webshop send `contract_version` / `tenant` / `causation_id`; email-service's folder
      documents `schema_version`. Both folders call theirs the estate's envelope.
- [ ] **booking-service's field error carries no `code`**, while the other six document one and
      `@lazslov/api-core` requires it. Either the documentation is short a member or the shared type
      is wrong — see [ai-context.md](../ai-context.md) § Open questions for what the SDK-side fix
      would cost.
